## Схема

```text
Нагрузочный скрипт (на хосте, 15 rps)
                  |
             localhost:8080
                  |
           kind extraPortMappings
                  |
       Kubernetes NodePort :30080
                  |
           Service hello :80
                  |
         EndpointSlice (Ready endpoints)
                  |
      +-----------+-----------+
      |           |           |
  Pod hello-1  Pod hello-2  Pod hello-3
  app :8080    app :8080    app :8080
  / /live      / /live      / /live
  /ready       /ready       /ready
```

Service направляет новые соединения к доступным endpoints; при удалении или изменении готовности Pod информация о маршрутах распространяется не мгновенно. Здесь один узел kind, поэтому отказ узла не покрывается.

## Сборка и запуск с чистого кластера

Команды выполнять из каталога `homework/hw1` (Docker Engine / Docker Desktop уже запущен, `kind` и `kubectl` установлены).

```bash
kind create cluster --name hw1 --config kubernetes/kind-config.yaml

docker build -f app/Dockerfile --build-arg APP_VERSION=v1 -t hw1-hello:v1 app
docker build -f app/Dockerfile --build-arg APP_VERSION=v2 -t hw1-hello:v2 app
kind load docker-image hw1-hello:v1 hw1-hello:v2 --name hw1

kubectl apply -f kubernetes/deployment.yaml -f kubernetes/service.yaml
kubectl rollout status deployment/hello --timeout=120s
kubectl get pods -l app=hello -o wide
kubectl get endpointslice -l kubernetes.io/service-name=hello -o wide
curl --max-time 2 http://127.0.0.1:8080/
```

Теги **v1/v2** заданы через build-arg → ENV; тег `latest` не используется. Конфигурация: 3 реплики, `maxUnavailable: 0`, `maxSurge: 1`, `requests/limits`, readiness `/ready`, liveness `/live`. Для graceful termination: `preStop: sleep 5`, `terminationGracePeriodSeconds: 30`, приложение обрабатывает SIGTERM и ожидает завершения активных обработчиков.

## План сбора доказательств

На время каждого сценария открыть терминал наблюдения:

```bash
kubectl get pods -l app=hello -w
```

В другом терминале наблюдать состояния EndpointSlice (команду можно перезапускать несколько раз):

```bash
kubectl get endpointslice -l kubernetes.io/service-name=hello -o yaml
```

Для проверки количества Ready-реплик:

```bash
kubectl get deployment hello -o jsonpath='{.status.readyReplicas}{"/"}{.spec.replicas}{" ready\n"}'
```

Для каждого сценария запустить **нагрузку отдельно**, затем во время ее работы выполнить действие в другом терминале. В проведённых испытаниях скрипт посылал 15 HTTP-запросов/с в течение 120 секунд с таймаутом 2 секунды; он сохраняет время, статус, тип ошибки, версию и Pod для каждого запроса в CSV и печатает сводку по итогам. Время старта действия записать отдельно. Во время измерения нельзя останавливать/монтировать вывод нагрузки.

## Эксперимент 1. Удаление Pod под нагрузкой

**Цель:** проверить доступность HTTP-сервиса при удалении одного из трёх Pod.

Нагрузка составляла 15 запросов/с в течение 120 секунд. Таймаут HTTP-запроса — 2 секунды. Через 17 секунд после начала нагрузки Pod `hello-d6759dd5f-65wxf` был удалён командой `kubectl delete pod` без принудительного завершения.

Команда нагрузки (выполнялась из `homework/hw1`):

```bash
python3 load/load.py --url http://localhost:8080/ --rps 15 --duration 120 --timeout 2 --output evidence/delete-pod.csv
```

## Эксперимент 2. Перевод Pod в NotReady

**Цель:** проверить исключение неготового Pod из маршрутизации Service без перезапуска контейнера.

Нагрузка: 15 запросов/с, 120 секунд, таймаут 2 секунды. Через временный Pod с curl отправлен `POST /unready` непосредственно на IP `hello-d6759dd5f-5jggn`. Нагрузочные запросы шли через Service по `http://localhost:8080/`.

EndpointSlice изменил готовность выбранного адреса `true → false → true`, Deployment — `3/3 → 2/3 → 3/3`. За 25 секунд наблюдаемого NotReady выполнено 375 запросов; ни один ответ не поступил от выбранного Pod. После `POST /ready-on` он снова обслуживал запросы. UID не изменился, перезапусков не было.

### Вывод

В данном испытании Kubernetes исключил NotReady Pod из набора готовых endpoints Service без удаления или перезапуска. Другие две реплики продолжали обслуживать запросы без зарегистрированных ошибок. После восстановления готовности Pod вернулся к обслуживанию.

Readiness определяет готовность получать трафик, liveness — необходимость перезапуска при неработоспособности процесса. Исключение из маршрутизации не мгновенно: есть задержки выполнения пробы и распространения обновлений endpoints.

## Эксперимент 3. RollingUpdate v1 → v2

**Цель:** проверить доступность при постепенной замене версии приложения.

Исходное состояние: три готовые реплики `hw1-hello:v1`. Нагрузка шла через `http://localhost:8080/`: 15 запросов/с, 120 секунд, таймаут 2 секунды. Через 17 секунд выполнено `kubectl set image deployment/hello hello=hw1-hello:v2`. Нагрузка продолжалась до конца заданного времени, в том числе после успешного `kubectl rollout status`.

### Результаты

| Метрика | Значение |
|---|---:|
| Всего запросов / HTTP 200 | 1800 / 1800 |
| Таймауты / HTTP 5xx / ошибки соединения | 0 / 0 / 0 |
| Ответы v1 | 355 |
| Ответы v2 | 1445 |
| Минимум / максимум Ready-реплик по журналу Deployment | 3 / 4 |
| `hello-d6759dd5f-5jggn` (v1) | 102 |
| `hello-d6759dd5f-kzhx5` (v1) | 136 |
| `hello-d6759dd5f-wzt5f` (v1) | 117 |
| `hello-59645cc658-d5lh4` (v2) | 503 |
| `hello-59645cc658-tp9bz` (v2) | 501 |
| `hello-59645cc658-msrxd` (v2) | 441 |

Первый запрос с ответом v2 начался в `1791907744.539`, последний с ответом v1 — в `1791907749.870` (Unix timestamp). Интервал между началами этих запросов — 5.331 секунды: ответы двух версий встречались в одном переходном окне. CSV фиксирует время начала запроса, а не получения ответа.

Сразу после успешного `rollout status` дополнительный curl ещё вернул v1 от завершающегося Pod. Позднее контрольный запрос вернул v2; остались три готовых Pod новой версии. Точная причина переходного ответа отдельно не установлена. Успешный rollout не следует трактовать как синхронное переключение всех клиентских запросов.

## Границы гарантий

В трёх испытаниях выполнено суммарно 5400 запросов без зарегистрированных ошибок. Это результат конкретных измерений, а не абсолютная гарантия доступности.

- `replicas: 3` обеспечивает резерв отдельных экземпляров, **не узлов**. В одноузловом kind отказ узла останавливает все реплики и Service.
- `maxUnavailable: 0` ограничивает действия контроллера **при плановом RollingUpdate**, но не обещает отсутствие ошибок при внезапном удалении Pod, задержках EndpointSlice/kube-proxy или сбоях сетевого пути.
- Readiness выключает Pod из числа **готовых маршрутов** и не рестартует его. Liveness инициирует перезапуск при устойчивой неработоспособности процесса, но не обнаружит неправильный бизнес-ответ `hello` или баг, при котором оба probe продолжают отдавать 200.
- Если **оба образа** имеют общий дефект или все реплики оказались not-ready, резервирование не помогает.
- `preStop` дает время для распространения изменения маршрутизации до SIGTERM; `terminationGracePeriodSeconds` ограничивает общий бюджет завершения, включая preStop. SIGTERM + ожидание активных обработчиков снижают риск потери запросов, но не гарантируют 0 ошибок, особенно при долгих соединениях и истечении grace period.
- `kubectl delete pod` — прямое удаление, **PDB его не запрещает**; PDB ограничивает добровольные выселения через API Eviction (например, при `kubectl drain`) и не защищает от сбоя узла. PDB здесь не нужен для демонстрации и не задан.
- Service балансирует на уровне соединений/сетевых правил, поэтому 15 запросов/с не означают равное распределение по Pod. Возможны задержки обновления сетевых правил и сохранение существующих соединений.
- Успешный `rollout status` не означает мгновенного прекращения ответов старой версии: в эксперименте контрольный запрос сразу после него вернул v1. Причина по собранным данным однозначно не установлена.
- Единственный локальный генератор нагрузки и NodePort на одном хосте тоже не отказоустойчивы. Результаты относятся к конкретному кластеру и конкретному короткому тесту, а не к доказанной доступности в процентах за год.

Перед повторным RollingUpdate проверить образ: после экспериментов развёрнута v2. Для демонстрации перехода v1 → v2 заранее вернуть v1 и дождаться готовности трёх реплик. После записи добавить настоящую ссылку и фактические таймкоды в начало README.
